# ai-canvas 项目分析与思路梳理

> 对应代码：`ai-canvas/`
> 运行命令：`pnpm install` → 配好 `.env` → `pnpm start:dev` → 打开 http://localhost:3000

一个「AI 画板」：输入文字生成图片，或者上传一张图 + 文字描述来改图，生成结果落到自己的 OSS，前端有列表页可以回看和删除。

技术栈：**NestJS 11 + 阿里云百炼（DashScope）通义万相 + 阿里云 OSS + 原生 HTML 单页**。

---

## 一、这个项目解决什么问题

表面上是「调个文生图 API」，但真正要解决的是**AI 生图落地时的三个工程问题**：

| 问题 | 现象 | 本项目的解法 |
|---|---|---|
| 用户图片怎么传给模型？ | 大模型只接受 **公网可访问的 URL**，不接受二进制文件 | 用户图先传到 OSS，把 OSS URL 给模型 |
| 图片流量不能压在 Node 上 | 10MB 图片走后端转发，占带宽、占内存、慢 | **前端直传 OSS**（后端只发签名，文件不经过 Node） |
| 模型返回的 URL 会过期 | DashScope 返回的图片 URL 只有几小时有效期 | **转存**：后端 fetch 下来重新 put 到自己 bucket |

再加一个隐含问题：**bucket 是私有的**，模型访问不了裸 URL → 所以给模型的 URL 必须现算一个**带签名的临时读链接**。

所以整个项目的核心其实是「**URL 的四次变身**」，这是理解代码的钥匙。

## 二、整体架构与数据流

### 完整链路（图生图模式）

```
┌─────────┐
│  浏览器  │
└────┬────┘
     │ ① GET /ai/oss/upload-signature?ext=.jpg
     ▼
┌──────────────┐   calculatePostSignature
│ Nest 后端     │──────────────────────────► 只做本地 HMAC 计算，不发网络请求
│ OssService   │
└────┬─────────┘
     │ 返回 { host, key, policy, Signature, url }
     ▼
┌─────────┐  ② POST form-data 直传（文件不经过 Node！）
│  浏览器  │ ─────────────────────────────────────► ┌──────────┐
└────┬────┘                                        │ 阿里云OSS │
     │                                             └──────────┘
     │ ③ POST /ai/image { prompt, imageUrl }
     ▼
┌────────────────────────────────────────────────────────┐
│ Nest 后端  AiService.createImage()                      │
│                                                        │
│  ④ resolveReadableUrl(imageUrl)                        │
│     私有 bucket 裸 URL → 带 Signature 的 1h 临时读链接    │
│                                                        │
│  ⑤ DashScope syncRequest                               │
│     wan2.6-image（有图）/ wan2.6-t2i（无图）             │
│     ⏳ 同步阻塞 1~3 分钟                                 │
│                                                        │
│  ⑥ uploadFromUrl(临时结果URL)                           │
│     fetch 下来 → put 到自己 bucket → 永久 key            │
│                                                        │
│  ⑦ imageStore.add(...) 内存数组存一条记录                 │
└────┬───────────────────────────────────────────────────┘
     │ 返回 ImageRecord { id, url, prompt, mode, size, createdAt }
     ▼
┌─────────┐
│  浏览器  │  渲染结果 + 刷新列表
└─────────┘
```

### URL 的四次变身（重点记这个）

```
1. 前端直传后的地址        https://bucket.region.aliyuncs.com/ai-canvas/uploads/xxx.jpg
                          （私有 bucket，直接访问 403）
                                    │ resolveReadableUrl()
                                    ▼
2. 给模型看的临时签名地址   .../xxx.jpg?OSSAccessKeyId=..&Expires=..&Signature=..
                          （1 小时有效，DashScope 服务端能读）
                                    │ 万相生成
                                    ▼
3. DashScope 返回的地址    https://dashscope-result-xx.oss-cn-xx.aliyuncs.com/...
                          （几小时后失效，不能直接存库）
                                    │ uploadFromUrl()
                                    ▼
4. 转存到自己 bucket 的地址 https://bucket.region.aliyuncs.com/ai-canvas/edited/xxx.png
                          （永久，写进 ImageRecord.url）
```

职责切得很清楚，**四层**：

```
Controller（只做路由/取参） → AiService（业务编排） → OssService / ImageStoreService（能力封装）
```

`AiService` 自己不碰 OSS 细节，也不碰存储细节，只负责「按什么顺序调」——这就是编排层该有的样子。

## 四、逐模块解析

### 1. `main.ts` —— `transform: true` 不是可选项

```ts
app.useGlobalPipes(new ValidationPipe({ transform: true }));
```

很多人以为 `transform` 只是「顺手加的」，但这个项目**必须开**。因为 `ImageDto` 里用了 `@Transform` 做 trim 和默认值：

- 不开 `transform`：`ValidationPipe` 校验完把**原始 plain object** 交给 handler，`@Transform` 的结果被丢掉 → `prompt` 没被 trim、`promptExtend` 拿不到默认值。
- 开 `transform`：handler 收到的是**转换后的 DTO 实例**，`@Transform` 生效。

记忆点：**`@Transform` 想生效，就得开 `transform: true`。**

### 2. `app.module.ts` —— 静态资源和 API 抢路由

```ts
ServeStaticModule.forRoot({
  rootPath: join(__dirname, '..', 'public'),
  exclude: ['/ai/*path'],   // ← 注意这个写法
})
```

`ServeStaticModule` 会兜住所有没匹配到的路径。如果不 `exclude`，`/ai/image/list` 可能被静态中间件拦下返回 404 HTML 而不是走 Controller。

`'/ai/*path'` 是 **Nest 11 / path-to-regexp v8** 的新语法——通配符必须**具名**。Nest 10 时代写 `'/ai/*'` 就行，升级到 11 之后裸 `*` 会直接抛错。这是升级 Nest 11 最常踩的坑之一。

`ConfigModule.forRoot({ isGlobal: true })`：全局注册，其他模块不用重复 import 就能注入 `ConfigService`。

### 3. `dto/image.dto.ts` —— 在边界上把数据洗干净

```ts
@IsString() @IsNotEmpty()
@Transform(({ value }) => typeof value === 'string' ? value.trim() : value)
prompt: string;

@IsOptional() @IsString()
@Transform(({ value }) =>
  typeof value === 'string' && value.trim() ? value.trim() : undefined)
imageUrl?: string;
```

两个设计意图：

1. **`imageUrl` 的空串归一化成 `undefined`**。这非常关键，因为 `AiService` 用 `inputImageUrl ? edit : text` 来选模型。前端如果传了 `imageUrl: ""`（很常见，比如输入框清空后没重置），空串是 falsy 所以其实也 OK，但归一成 `undefined` 后 `mode` 字段、日志、后续判断都干净一致——**在边界统一表示法，内部就不用到处防御**。
2. **`typeof value === 'string'` 的判断**是防注入：如果攻击者传 `imageUrl: {toString: ...}` 或数组，`.trim()` 会抛异常。先判类型再操作。

```ts
@Transform(({ value }) => value ?? true)  promptExtend?: boolean;
```

`promptExtend`（提示词智能扩写）默认 true、`watermark` 默认 false。注意 `AiService` 里又写了一遍 `dto.promptExtend ?? true`——**默认值写了两处，是冗余**。生产代码里应该只留一处（推荐留 DTO，因为它是边界），否则改默认值时容易漏。

### 4. `ai.controller.ts` —— 薄到只剩路由

```ts
@Get('oss/upload-signature')  getUploadSignature(@Query('ext') ext?: string)
@Get('image/list')            listImages()
@Post('image')                createImage(@Body() dto: ImageDto)
@Delete('image/:id')          deleteImage(@Param('id') id: string)
```

37 行，没有一行业务逻辑，全部转发给 `AiService`。这是刻意的：**Controller 只做协议适配（HTTP → 方法调用），换成 GraphQL / gRPC 时 Service 一行不用改。**

注意 `@Get('oss/upload-signature')` 写在 `@Get('image/list')` 前面无所谓，但如果有 `@Get(':id')` 这种通配路由，就必须放在具体路由之后——Nest 按声明顺序匹配。

### 5. `ai.service.ts` —— 编排层

#### createImage：整个项目的主流程

```ts
const resultUrl = inputImageUrl
  ? await this.generateByEdit(
      [{ text: dto.prompt },
       { image: this.ossService.resolveReadableUrl(inputImageUrl) }],  // ← 换签名 URL
      options)
  : await this.generateByText([{ text: dto.prompt }], options);

const url = await this.ossService.uploadFromUrl(resultUrl);            // ← 转存
return this.imageStore.add({ ..., mode: inputImageUrl ? 'edit' : 'text' });
```

**有图走编辑模型，没图走文生图模型**——一个 `?:` 完成模式分发。多模态入参是数组 `[{text}, {image}]`，顺序有讲究：通常 text 在前、image 在后（也可多图）。

#### 两个模型的差异

| | 文生图 | 图像编辑 |
|---|---|---|
| model | `wan2.6-t2i` | `wan2.6-image` |
| size | `1280*1280`（像素） | `1K`（档位） |
| 额外参数 | — | `enable_interleave: false` |
| 入参 content | `[{text}]` | `[{text}, {image}]` |

`size` 两个模型的表示法完全不同（`1280*1280` vs `1K`），所以 `ImageDto.size` 只能是 `string` 不能做强类型枚举。这也是为什么 `imageStore` 里存的 `size` 要在 service 里兜底：`options.size ?? (inputImageUrl ? '1K' : '1280*1280')`。

#### `wanCall` —— 绕过 SDK 类型定义的写法

```ts
interface MultiModalConversationInternal {
  syncRequest(data: Record<string, unknown>): Promise<GenerationResult>;
}

return (this.client as unknown as MultiModalConversationInternal).syncRequest({
  model,
  input: { messages },
  parameters: { ...rest, stream: false },
});
```

`dashscope-sdk-official` 的 `MultiModalConversation` 类型定义里没有暴露 `syncRequest`（或者签名不匹配万相的参数），所以这里：

1. 自己声明一个「内部接口」描述真实存在的方法；
2. `as unknown as X` 双重断言强转（TS 不允许不相关类型直接断言，得先过 `unknown`）。

**这是对付 SDK 类型定义落后于实际 API 的标准手法**——比 `any` 好，因为至少 `syncRequest` 的入参出参还有类型；比 `@ts-ignore` 好，因为意图明确。

同时注意 DashScope 的请求体结构是固定的三层：`{ model, input: { messages }, parameters: {...} }`。`wanCall` 把这个结构封装掉，调用方只需要平铺写 `{ model, messages, size, watermark }`，用 `...rest` 自动塞进 `parameters`。

#### 两层错误校验

```ts
private assertSuccess(result) {
  if (result.status_code !== 200 || result.code) throw new BadRequestException(...);
}
private extractImageUrl(result) {
  return result.output?.choices?.[0]?.message?.content?.find(i => i.image)?.image;
}
```

DashScope 的坑：**HTTP 200 不代表业务成功**，业务错误藏在 body 的 `status_code` / `code` 字段里。所以必须显式 `assertSuccess`。

`extractImageUrl` 返回 `undefined` 时抛错并**把整个 result JSON 塞进错误信息**——调试期这样做很实用，但生产环境要去掉（可能泄漏内部信息，且响应体很大）。

### 6. `oss.service.ts` —— 项目最有料的文件

#### 为什么建两个 OSS client

```ts
this.client     = new OSS({ ..., authorizationV4: true });  // put / signatureUrl
this.postClient = new OSS({ ... });                          // calculatePostSignature
```

同样的密钥、同样的 bucket，唯一区别是 `authorizationV4`：

- **`client`（V4）**：用于后端 `put()` 上传和 `signatureUrl()` 生成读链接。V4 是阿里云现在推荐的签名算法，安全性更好。
- **`postClient`（V1）**：专门算 PostPolicy。如果开 V4，`calculatePostSignature` 返回的字段名会变成 `x-oss-signature-version` / `x-oss-credential` / `x-oss-date` / `x-oss-signature` 这一套，前端表单字段要跟着全改。这里故意用 V1，保持经典的 `OSSAccessKeyId / policy / Signature` 三件套，**前端表单最简单**。

这是个典型的**教学向权衡**：新算法更安全，但老算法的前端代码更容易讲清楚。生产项目应该统一到 V4。

#### `trimEnv` —— 两个防御

```ts
private trimEnv(key: string): string {
  return this.config.getOrThrow<string>(key).trim();
}
```

- `getOrThrow`：环境变量缺失时**启动就崩**，而不是等到用户点上传才 500。这叫 fail fast。
- `.trim()`：防 `.env` 复制粘贴带上的尾随空格/换行。AccessKeySecret 多一个空格就是 `SignatureDoesNotMatch`，而且报错信息完全看不出是空格问题——**这行 `.trim()` 能省你两小时**。

#### `createUploadPolicy` —— 前端直传的安全边界

```ts
const key = `${prefix}/${Date.now()}-${randomUUID()}${normalizedExt}`;

const policy = {
  expiration: expire.toISOString(),        // 1 小时后失效
  conditions: [
    ['content-length-range', 0, 1048576000],
    ['eq', '$key', key],                   // ← 锁死 key
  ],
};
const signature = this.postClient.calculatePostSignature(policy);
```

四道防线，每一道都对应一个真实攻击场景：

| 措施 | 防什么 |
|---|---|
| `key` 由**后端**生成（时间戳 + UUID） | 前端自定路径 → 覆盖别人的文件 / 目录穿越 |
| `['eq', '$key', key]` | 拿到签名后改 key 上传到任意路径 |
| `['content-length-range', 0, N]` | 上传超大文件打爆你的 OSS 账单 |
| `expiration` 1 小时 | 签名被截获后长期复用 |

**关键认知：`calculatePostSignature` 是纯本地 HMAC 计算，不发网络请求。** 所以「获取签名」这个接口极快（毫秒级），可以放心每次上传都调一次。

⚠️ 这里 `content-length-range` 上限是 `1048576000`（约 1000MB），太宽松了。前端限了 10MB，但攻击者可以绕过前端直接 POST 到 OSS。**服务端的限制才是真限制**，应该收到 10MB。

#### `resolveReadableUrl` —— 私有 bucket 的读取

```ts
const host = `${this.bucket}.${this.region}.aliyuncs.com`;
if (!imageUrl.includes(host)) return imageUrl;   // 外部 URL 原样返回

const objectKey = decodeURIComponent(new URL(imageUrl).pathname.slice(1));
return this.getSignedUrl(objectKey);             // 自己的 → 换签名 URL
```

三个细节：

1. **先判断是不是自己的 URL**。用户可能直接粘贴一个外网图片地址，那就不用签名，原样透传给模型。
2. `pathname.slice(1)` 去掉开头的 `/`（objectKey 不带前导斜杠）。
3. `decodeURIComponent` 还原中文/空格——URL 里是 `%E4%B8%AD%E6%96%87.jpg`，但 objectKey 是 `中文.jpg`，不解码签名会算错。

#### `uploadFromUrl` —— 转存

```ts
const response = await fetch(sourceUrl);
if (!response.ok) throw new InternalServerErrorException(...);
const buffer = Buffer.from(await response.arrayBuffer());
return (await this.uploadBuffer(buffer, prefix, 'result.png')).url;
```

为什么必须转存？**DashScope 返回的 URL 是临时的**（一般几小时到 24 小时）。如果直接把它写进数据库，用户明天打开列表全是裂图。

代价是**整张图进内存**（`arrayBuffer()`）。图片几 MB 无所谓，但如果换成视频生成就必须改成流式 `putStream`。

#### `wrapOssError` —— 错误码翻译成人话

```ts
if (ossError.code === 'InvalidAccessKeyId')
  return new InternalServerErrorException('OSS AccessKeyId 无效，请检查 .env 中的 OSS_ACCESS_KEY_ID ...');
if (ossError.code === 'SignatureDoesNotMatch')
  return new InternalServerErrorException('OSS AccessKeySecret 不正确，请检查 ...');
if (ossError.code === 'NoSuchBucket')
  return new InternalServerErrorException('OSS Bucket 不存在，请检查 OSS_BUCKET 和 OSS_REGION 是否匹配');
```

把 OSS 三个最高频错误码翻译成「**该改哪个环境变量**」。这个模式很值得抄：新人配环境时看到 `SignatureDoesNotMatch` 一脸茫然，看到「请检查 OSS_ACCESS_KEY_SECRET」立刻就知道干什么。

同时注意：**原始错误进 logger，对外统一 `InternalServerErrorException`**，不把密钥相关的堆栈泄漏给前端。

注意方法名是 `wrap` 且 **`return` 而不是 `throw`**，调用方写 `throw this.wrapOssError(...)`。这样做的好处是 TS 能正确推断控制流（返回 `Error` 类型，调用处 `throw` 后代码不可达）。

### 7. `image-store.service.ts` —— 内存版数据库

```ts
private readonly items: ImageRecord[] = [];

list()   { return [...this.items].sort((a, b) =>
             new Date(b.createdAt).getTime() - new Date(a.createdAt).getTime()); }
add()    { this.items.unshift(item); }
remove() { index === -1 ? throw new NotFoundException(...) : this.items.splice(index, 1); }
```

三个点：

1. **`[...this.items]` 再 sort**：`Array.prototype.sort` 是**原地排序**，直接 `this.items.sort()` 会改动内部状态。拷贝一份再排，保证 `list()` 是纯读操作。
2. `unshift` + 再按 `createdAt` 排序是**双重保险**（unshift 已经保证新的在前）。
3. **重启即丢失**。这是 demo 的取舍。因为 Service 是单例（Nest 默认 `DEFAULT` scope），数组在进程生命周期内共享——换成多实例部署就直接失效了。

替换成真数据库时，只要保持 `list/add/remove` 三个方法签名不变，`AiService` 一行不用改——这就是把存储抽成独立 Service 的收益。

### 8. `public/index.html` —— 前端直传的完整实现

#### 上传三步

```js
async function uploadToOSS(file) {
  const ext = file.name.match(/\.[^.]+$/)?.[0] || '.jpg';
  const ossInfo = await getOSSInfo(ext);            // ① 要签名

  const formdata = new FormData();
  formdata.append('key', ossInfo.key);
  formdata.append('OSSAccessKeyId', ossInfo.OSSAccessKeyId);
  formdata.append('policy', ossInfo.policy);
  formdata.append('signature', ossInfo.Signature);  // ← 注意大小写！
  formdata.append('success_action_status', '200');
  formdata.append('file', file);                    // ← file 必须最后 append

  try { await fetch(ossInfo.host, { method: 'POST', body: formdata }); }
  catch { /* 请求已发出，通常已上传成功 */ }

  return ossInfo.url;                               // ② 直接返回预先算好的 URL
}
```

**四个必须记住的坑：**

1. **表单字段名 `signature` 是小写**，而后端返回的字段叫 `Signature`（SDK 的返回值命名）。OSS PostObject 协议要求的字段名是小写 `signature`（`OSSAccessKeyId`、`policy` 又是特定大小写）。写错就是 400。
2. **`file` 必须是最后一个 append 的字段**。OSS 是流式解析 multipart 的，遇到 `file` 就开始写对象，后面的字段会被忽略。
3. **`success_action_status: '200'`**：不加的话 OSS 成功返回 **204 No Content**，某些封装库会当成异常。
4. **`try/catch` 吞掉错误**：如果 bucket 没配 CORS，浏览器读不到响应会抛 network error，但**文件其实已经上传成功了**。所以这里 catch 后照样返回 URL。⚠️ 这是个偷懒做法——真正的错误（比如签名过期）也被吞了。正确做法是给 bucket 配好 CORS 规则（允许 POST、暴露 ETag），然后检查 `response.ok`。

**为什么能提前知道 URL？** 因为 `key` 是后端生成的、policy 里又用 `eq` 锁死了，所以最终地址 `host/key` 在上传前就是确定的——不需要等 OSS 返回。

#### 「选完图自动生成」的交互

```js
fileInput.addEventListener('change', async () => {
  if (file.size > 10 * 1024 * 1024) { alert('图片不能超过 10MB'); return; }
  pendingFile = file;
  uploadedImageUrl = null;                        // ← 换图要清缓存
  uploadedImageUrl = await ensureUploaded();
  if (promptEl.value.trim()) await generateImage();  // 有描述就直接生成
  else statusEl.textContent = '图片已上传，请填写描述后点击生成';
});
```

`ensureUploaded()` 做了**幂等缓存**：

```js
async function ensureUploaded() {
  if (uploadedImageUrl) return uploadedImageUrl;   // 已上传过，直接复用
  if (!pendingFile) return null;
  ...
}
```

所以用户「选图 → 自动生成 → 改 prompt → 再点生成」时，第二次不会重复上传同一张图。换图时手动 `uploadedImageUrl = null` 让缓存失效。

#### XSS 防护

```js
function escapeHtml(str) {
  return str.replace(/[&<>"']/g, (c) => ({'&':'&amp;','<':'&lt;',...})[c]);
}
// 列表渲染
<div class="card-prompt">${escapeHtml(item.prompt)}</div>
<img class="thumb" src="${item.url}" />       // ← url 没转义
```

`prompt` 是**用户输入**，用 `innerHTML` 拼接必须转义，否则 prompt 里写 `<img onerror=...>` 就是存储型 XSS。
`item.url` 没转义是因为它由**后端生成**（时间戳+UUID+固定 host），不含用户可控内容。这个判断是对的，但属于「靠上下文保证安全」——如果哪天 key 改成用文件名，就会有漏洞。

## 五、关键设计决策（面试可讲的点）

| 决策 | 为什么 | 代价 |
|---|---|---|
| **前端直传 OSS**，后端只发签名 | 图片流量不过 Node，省带宽/内存，上传快 | 需要处理 CORS、签名安全边界 |
| **key 由后端生成 + policy 锁 key** | 防覆盖、防目录穿越 | 前端拿不到自定义命名能力 |
| **转存 DashScope 结果** | 模型返回的 URL 会过期 | 多一次下载+上传，整图进内存 |
| **私有 bucket + 签名读 URL** | 图片不被公开爬取 | 每次给模型都要现算签名 |
| **两个 OSS client（V4/V1）** | PostPolicy 用 V1 前端表单最简单 | 签名算法不统一，理解成本高 |
| **同步调用模型（syncRequest）** | 代码最简单，教学清晰 | HTTP 请求阻塞 1~3 分钟，极易超时 |
| **内存存储 ImageRecord** | demo 零依赖 | 重启丢数据，不能多实例 |
| **Controller 极薄 / 三层分离** | Service 可复用、可换协议 | 文件数量多 |

最值得讲的一条：**「前端直传 + 后端签名」是所有文件上传场景的标准架构**。核心思想是——把**权限决策**（能不能传、传到哪、多大）留在后端，把**数据传输**交给客户端和存储服务直连。

## 六、环境配置（`.env`）

```bash
OPENAI_API_KEY=              # 百炼 DashScope API Key（sk-xxx）
OSS_REGION=oss-cn-beijing    # 必须带 oss- 前缀，且与 bucket 地域一致
OSS_ACCESS_KEY_ID=           # 阿里云 RAM 用户 AccessKey（不是 DashScope Key！）
OSS_ACCESS_KEY_SECRET=
OSS_BUCKET=

OSS_PREFIX=ai-canvas/edited          # 生成结果存放前缀
OSS_UPLOAD_PREFIX=ai-canvas/uploads  # 用户上传前缀
```

**两把钥匙别搞混**：
- `OPENAI_API_KEY` → 百炼控制台的 DashScope API Key，调模型用
- `OSS_ACCESS_KEY_*` → 阿里云 RAM 用户的 AccessKey，操作 OSS 用

**`OSS_REGION` 必须带 `oss-` 前缀**，因为代码里直接拼 host：`https://${bucket}.${region}.aliyuncs.com`。填 `cn-beijing` 会拼出 `bucket.cn-beijing.aliyuncs.com`（错的），要填 `oss-cn-beijing`。

bucket 还需要在控制台配 **CORS 规则**：来源 `*`（生产填具体域名）、允许方法 `POST`、允许 Headers `*`。

## 八、生产化改进清单

| 问题 | 现状 | 改进 |
|---|---|---|
| 请求阻塞 1~3 分钟 | `syncRequest` 同步等 | 改**异步任务**：立即返回 taskId，用 SSE/WebSocket 推送进度，或轮询 DashScope 异步接口 |
| 数据重启丢失 | 内存数组 | Postgres / MongoDB，`ImageStoreService` 接口不变 |
| 上传大小限制太宽 | policy 允许 ~1GB | `content-length-range` 收到 10MB，与前端一致 |
| CORS 错误被吞 | 前端 `catch {}` 空实现 | 配好 bucket CORS，检查 `response.ok` |
| 签名算法不统一 | V4 + V1 混用 | 统一 V4，前端表单改用 `x-oss-*` 字段 |
| 无用户隔离 | 所有人共享一个列表 | key 加 `userId` 前缀，记录带 `userId`，列表按用户过滤 |
| 错误信息泄漏 | 抛错时带整个 DashScope JSON | 只对外抛简短信息，详情进日志 |
| 无限流 | 谁都能无限调 | `@nestjs/throttler` + 按用户配额（生图很贵） |
| 私有图无法在列表显示 | `ImageRecord.url` 是裸 URL | 列表返回时也走 `resolveReadableUrl`，或结果图放公共读 bucket |
| 默认值重复定义 | DTO 和 Service 各写一遍 | 只留 DTO 一处 |

## 九、API 速查

| 方法 | 路径 | 入参 | 返回 |
|---|---|---|---|
| GET | `/ai/oss/upload-signature` | `?ext=.jpg` | `{ host, key, url, OSSAccessKeyId, policy, Signature, expire }` |

**OssService 方法速查：**

| 方法 | 作用 | 关键点 |
|---|---|---|
| `createUploadPolicy(ext)` | 生成前端直传签名 | 纯本地计算，不发网络请求 |
| `resolveReadableUrl(url)` | 裸 URL → 签名读 URL | 非本 bucket 的原样返回 |
| `uploadBuffer(buf, prefix, name)` | Buffer 上传 | key = `prefix/时间戳-uuid.ext` |
| `getSignedUrl(key, expires)` | 生成临时读链接 | 默认 3600 秒 |
| `uploadFromUrl(url)` | 外链转存到本 bucket | 整图进内存 |

## 十、一句话复述（记忆锚点）

> **ai-canvas 的本质是「URL 搬运工」**：
> 后端发个**带 policy 锁定的直传签名**让浏览器把图直传 OSS（省带宽），
> 再把私有 OSS 地址**换成 1 小时签名 URL** 喂给通义万相（模型只认公网 URL），
> 最后把万相返回的**临时结果 URL 转存回自己 bucket**（防过期）。
>
> 三层 Nest 结构：Controller 只路由 → AiService 只编排 → OssService/ImageStore 提供能力。
