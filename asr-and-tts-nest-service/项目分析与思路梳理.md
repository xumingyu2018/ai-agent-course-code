# asr-and-tts-nest-service 项目分析与思路梳理

> 一个基于 NestJS 的「豆包同款」语音交互服务：**语音提问（ASR）→ 大模型流式回答（SSE）→ 流式语音朗读（WebSocket + 腾讯云流式 TTS）**。

---

## 一、这个项目解决什么问题

常见 Agent（豆包、ChatGPT 语音模式）的语音交互包含两个方向：

| 方向 | 技术 | 是否流式 | 原因 |
|---|---|---|---|
| 语音 → 文字 | ASR（也叫 STT） | 不需要 | 用户说完一整段话再识别即可 |
| 文字 → 语音 | TTS | **必须流式** | 大模型回答是流式生成的，不可能等全部生成完再合成播放 |

**核心难点**：LLM 的文字通过 SSE 流式返回，但 SSE 是基于 HTTP 的**文本协议**，传二进制音频需要转 Base64（体积膨胀约 1/3），不适合。所以采用**双通道**方案：

- **SSE 通道**：流式返回文字（渲染聊天气泡）
- **WebSocket 通道**：流式推送二进制音频（播放语音）

两个通道通过 `sessionId` 关联，服务端内部用 **EventEmitter 事件** 打通。

## 二、整体架构与数据流

```
┌─────────┐  ①录音上传(FormData)   ┌──────────────────┐   SentenceRecognition  ┌──────────┐
│         │ ────────────────────▶ │ SpeechController  │ ─────────────────────▶ │ 腾讯云ASR │
│         │ ◀──────{text}──────── │  /speech/asr      │ ◀───── 识别文本 ─────── │  (HTTP)  │
│         │                       └──────────────────┘                        └──────────┘
│         │
│  浏览器  │  ②先连 WS 拿 sessionId  ┌──────────────────┐
│ (前端页) │ ◀───{type:session}──── │  main.ts 里的      │
│         │    /speech/tts/ws      │  WebSocketServer  │──registerClient──┐
│         │                        └──────────────────┘                  ▼
│         │  ③带 ttsSessionId 发起  ┌──────────────────┐   emit 事件   ┌────────────────┐
│         │ ── SSE /ai/chat/stream▶│ AiController      │ ───────────▶ │ TtsRelayService │
│         │ ◀── 流式文字(SSE) ───── │ AiService(chain)  │ start/chunk  │  (@OnEvent)     │
│         │                        └──────────────────┘  /end/error   └───────┬────────┘
│         │                                                                   │ wss(带签名)
│         │  ④二进制音频块(WS) ◀──────────────────────────────────────┐        ▼
│         │     MediaSource 流式播放                                  │  ┌──────────────┐
└─────────┘                                                          └──│ 腾讯云流式TTS  │
                                                                        │ stream_wsv2  │
                                                                        └──────────────┘
```

一次完整的语音对话时序：

1. 页面加载后（或提问前）连接 `ws://.../speech/tts/ws`，服务端生成 `sessionId` 并通过 `{type:'session', sessionId}` 返回
2. 用户录音 → `POST /speech/asr` → 得到识别文字
3. 用识别文字发起 `GET /ai/chat/stream?query=xxx&ttsSessionId=xxx`（SSE）
4. 服务端 LLM 每产出一个 chunk：SSE 推给前端渲染 + emit 事件给 TtsRelayService 转发给腾讯云 TTS
5. 腾讯云回传的二进制音频块经 WS 中继给前端，前端用 `MediaSource.appendBuffer` 边收边播

## 四、逐模块解析

### 1. AI 模块 —— SSE 流式回答

**ai.module.ts**：用 `useFactory` + `ConfigService` 创建 `ChatOpenAI` 实例注册为 `'CHAT_MODEL'` token。走 OpenAI 兼容协议，`.env` 里配 `OPENAI_BASE_URL`（如阿里云 DashScope）+ `MODEL_NAME`（如 qwen-plus）。

**ai.service.ts**：
- 构造 LCEL chain：`PromptTemplate → model → StringOutputParser`
- `streamChain()` 是 **async generator**，`for await` 消费 chain 的流，逐 chunk `yield`
- 关键点：每个 chunk 在 yield 给 SSE 之前，**同时 emit 一个 `chunk` 事件**（携带 sessionId），这就是文字流"分叉"给 TTS 的地方
- 流结束 emit `end` 事件；异常 emit `error` 事件

**ai.controller.ts**：
- `@Sse('chat/stream')` 装饰器实现 SSE，返回 RxJS `Observable`
- `from(asyncGenerator).pipe(map(...))` 把 async generator 转成 Observable
- 如果请求带了 `ttsSessionId`，先 emit `start` 事件（触发中继服务预连腾讯云）

### 2. Speech 模块 —— ASR 识别

**speech.controller.ts**：`POST /speech/asr`
- `@UseInterceptors(FileInterceptor('audio'))`：拦截器解析 multipart 表单的 `audio` 字段
- `@UploadedFile()` 把文件对象注入 handler 参数

**speech.service.ts**：
- 音频 buffer 转 Base64，调腾讯云 `SentenceRecognition`（一句话识别，HTTP 非流式）
- `VoiceFormat: 'ogg-opus'` 对应前端 MediaRecorder 的 `audio/ogg;codecs=opus` 录音格式
- `EngSerViceType: '16k_zh'`：16k 采样率中文引擎

### 3. TtsRelayService —— 项目核心（中继/桥接）

这是整个项目最复杂的部分，本质是一个**双向 WebSocket 桥**：

```
前端 clientWs ◀── TtsRelayService ──▶ 腾讯云 tencentWs
```

**会话管理**：`Map<sessionId, ClientSession>`，每个会话保存：
- `clientWs`：前端连接
- `tencentWs`：腾讯云连接（懒创建，收到 `start` 事件才连）
- `ready`：腾讯云是否已就绪（回了 `{ready:1}`）
- `pendingChunks`：**缓冲队列** —— 腾讯云还没 ready 时到达的文本先排队，ready 后 flush
- `closed`：防止重复关闭

**事件处理（@OnEvent 监听 `ai.tts.stream`）**：

| 事件 | 处理 |
|---|---|
| `start` | `ensureTencentConnection()` 建立/复用腾讯云 WS；通知前端 `tts_started` |
| `chunk` | 腾讯云已 ready → 直接发 `ACTION_SYNTHESIS`；未 ready → 入 `pendingChunks` 队列 |
| `end` | flush 队列后发 `ACTION_COMPLETE`（告诉腾讯云没有更多文本） |
| `error` | 通知前端 `tts_error` 并关闭会话 |

**腾讯云消息处理**（tencentWs.on('message')）：
- **二进制帧**（MP3 音频块）→ 原样透传给前端 `clientWs.send(data, {binary:true})`
- 文本帧（JSON）：
  - `ready === 1` → 标记就绪 + `flushPendingChunks()`
  - `code !== 0` → 转发 `tts_error` 给前端并关会话
  - `final === 1` → 转发 `tts_final`（前端据此 endOfStream）

**签名鉴权**（`buildTencentTtsWsUrl`）：腾讯云 WS 接口的固定套路：
1. 参数按 key 字典序排序拼成 `k=v&k=v`
2. 前缀拼 `GETtts.cloud.tencent.com/stream_wsv2?` 得到签名原文
3. HMAC-SHA1(secretKey) + Base64 得到 Signature
4. 全部参数 + Signature 放进 query string 组成 `wss://` URL

### 4. main.ts —— 手动挂载 WebSocketServer

没有用 `@nestjs/websockets` 网关，而是直接用 `ws` 包：

```ts
const ttsWss = new WebSocketServer({ server: app.getHttpServer(), path: '/speech/tts/ws' });
```

- 复用 Nest 的 HTTP server（同端口 3000），只处理 `/speech/tts/ws` 路径的 upgrade
- 连接建立后调 `ttsRelayService.registerClient(socket)` 注册会话、下发 sessionId
- 断开时 `unregisterClient` 清理

### 5. 事件契约 —— common/stream-events.ts

```ts
export const AI_TTS_STREAM_EVENT = 'ai.tts.stream';
export type AiTtsStreamEvent =
  | { type: 'start'; sessionId: string; query: string }
  | { type: 'chunk'; sessionId: string; chunk: string }
  | { type: 'end'; sessionId: string }
  | { type: 'error'; sessionId: string; error: string };
```

AI 模块（生产者）和 Speech 模块（消费者）只依赖这个契约，互不 import 对方 —— **用 `@nestjs/event-emitter` 解耦**，emit 方 `EventEmitter2.emit()`，消费方 `@OnEvent()` 自动触发。

### 6. 前端（asr-ai-stream.html）关键点

**录音**：`navigator.mediaDevices.getUserMedia({audio:true})` + `MediaRecorder`（优先 `audio/ogg;codecs=opus`），chunks 拼成 Blob 放 FormData 上传。

**双通道**：
- `new WebSocket('/speech/tts/ws')`，`ws.binaryType = 'arraybuffer'`，先等 `{type:'session'}` 拿 sessionId
- `new EventSource('/ai/chat/stream?query=..&ttsSessionId=..')` 接收流式文字

**流式播放（MediaSource 三件套）**：
```
audio.src = URL.createObjectURL(new MediaSource())
  → sourceopen 后 addSourceBuffer('audio/mpeg')，mode = 'sequence'
  → WS 每收到二进制块 → 入队 → sourceBuffer.appendBuffer(chunk)
  → appendBuffer 是异步的，必须等 updateend 再 append 下一块（所以要队列 + updating 检查）
  → 收到 tts_final → mediaSource.endOfStream()
```

## 五、关键设计决策（面试可讲的点）

1. **为什么文字用 SSE、音频用 WebSocket？**
   SSE 基于 HTTP，简单、自动重连，适合单向文本流；但传二进制得 Base64（+33% 体积）。WS 原生支持二进制帧，适合音频。各取所长。

2. **两个通道怎么关联？**
   前端先连 WS 拿到服务端生成的 `sessionId`，再把它作为 query 参数带进 SSE 请求。服务端事件里都带 sessionId，中继服务据此找到对应的前端 socket。

3. **为什么用 EventEmitter 而不是直接调用？**
   AI 模块和 Speech 模块解耦：AiService 不需要知道 TTS 中继的存在，只管广播"我生成了一段文字"。以后加别的消费者（比如日志、字幕）也不用改 AI 模块。

4. **pendingChunks 缓冲队列解决什么问题？**
   时序竞争：LLM 第一个 chunk 可能比腾讯云 WS 的 `ready:1` 先到。没 ready 就发会丢失/报错，所以先排队，ready 后统一 flush。

5. **前端为什么需要 appendBuffer 队列？**
   `SourceBuffer.appendBuffer` 是异步的，`updating` 期间再 append 会抛异常。所以音频块先入队，靠 `updateend` 事件驱动逐块消费。

6. **腾讯云流式 TTS 的协议要点**：
   URL 签名（排序 + HMAC-SHA1）→ 连接后等 `{ready:1}` → 逐段发 `ACTION_SYNTHESIS` → 发 `ACTION_COMPLETE` 收尾 → 二进制帧是音频、文本帧是控制消息 → `{final:1}` 表示结束。

## 八、一句话复述（记忆锚点）

> 录音用 MediaRecorder 上传给 `/speech/asr` 转文字；文字请求 `/ai/chat/stream` SSE 流式回答；SSE 生成每个 chunk 时通过 EventEmitter 事件推给 TtsRelayService，它维护 sessionId → socket 的会话表，把文本转发给腾讯云流式 TTS 的 WS 接口，收到的二进制音频原样中继给前端 WS；前端用 MediaSource + SourceBuffer 队列实现边收边播。**一个 SSE 通道传文字，一个 WS 通道传语音，sessionId 关联，事件解耦。**
